あなたは熟練したPythonバックエンドエンジニアです。
以下の要件に基づいて、社内ファイルサーバー検索ツールのバックエンドを実装してください。

# 1. 目的

社内ファイルサーバー上に大量に存在する設計書、問い合わせ資料、障害対応資料などを検索できるツールを作成する。

対象ファイルをPythonでスキャンし、ファイル名、フルパス、フォルダ階層、更新日時、本文抽出結果、文書種別、ベクトル情報などをPostgreSQLに登録する。

検索時はFastAPIで作成した検索APIを呼び出し、PostgreSQLのメタデータ検索、キーワード検索、pgvectorによるベクトル検索を組み合わせて、根拠付きの検索結果を返す。

Dify連携は後続工程で実施するため、今回はDify本体の実装は不要。
ただし、DifyのTool Nodeから呼び出しやすいJSON形式の検索APIを作成すること。

## 5.2 t_scan_run

スキャン実行履歴を管理する。

```sql
CREATE TABLE t_scan_run (
    scan_run_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at TIMESTAMPTZ,
    status VARCHAR(20) NOT NULL DEFAULT 'running',
    root_paths JSONB NOT NULL DEFAULT '[]'::jsonb,
    total_files_found INTEGER NOT NULL DEFAULT 0,
    inserted_count INTEGER NOT NULL DEFAULT 0,
    updated_count INTEGER NOT NULL DEFAULT 0,
    skipped_count INTEGER NOT NULL DEFAULT 0,
    deleted_marked_count INTEGER NOT NULL DEFAULT 0,
    error_count INTEGER NOT NULL DEFAULT 0,
    message TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT chk_scan_run_status
      CHECK (status IN ('running', 'success', 'failed', 'partial_success'))
);
```

ファイル単位の情報を管理する。

```sql

    path_hash CHAR(64) NOT NULL,

    file_name TEXT NOT NULL,
    extension VARCHAR(20) NOT NULL,
    parent_path TEXT NOT NULL,

    file_size BIGINT NOT NULL DEFAULT 0,
    last_modified_at TIMESTAMPTZ,

    status VARCHAR(20) NOT NULL DEFAULT 'active',
    is_archive BOOLEAN NOT NULL DEFAULT FALSE,
    archive_reason TEXT,

    system_name TEXT,
    project_name TEXT,
    document_type TEXT,
    year_label TEXT,
    version_label TEXT,

    latest_group_key TEXT,
    is_latest_candidate BOOLEAN NOT NULL DEFAULT FALSE,

    folder_keywords TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[],
    path_keywords TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[],

    search_text TEXT NOT NULL DEFAULT '',
    content_preview TEXT,

    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,

    first_seen_scan_run_id UUID REFERENCES t_scan_run(scan_run_id),
    last_seen_scan_run_id UUID REFERENCES t_scan_run(scan_run_id),
```

## 5.5 t_file_acl

ファイル閲覧権限を管理する。
初期実装ではCSVインポートまたは手動登録を想定し、Windows ACLの完全自動取得は必須ではない。

```sql
CREATE TABLE t_file_acl (
    file_id UUID NOT NULL REFERENCES t_file(file_id) ON DELETE CASCADE,

    principal_type VARCHAR(20) NOT NULL,
    principal_name TEXT NOT NULL,

    permission VARCHAR(30) NOT NULL DEFAULT 'read',
    can_read BOOLEAN NOT NULL DEFAULT TRUE,
    inherited BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    PRIMARY KEY (file_id, principal_type, principal_name, permission),

    CONSTRAINT chk_t_file_acl_principal_type
      CHECK (principal_type IN ('user', 'group')),
    CONSTRAINT chk_t_file_acl_permission
      CHECK (permission IN ('read', 'write', 'full_control'))
);
```

# 7. ファイルスキャンCLI

app/cli.pyにCLIを実装する。

以下のコマンドを用意する。

```bash
python -m app.cli scan --config config.yaml
python -m app.cli scan --config config.yaml --full
python -m app.cli show-config --config config.yaml
python -m app.cli load-acl-csv --csv acl.csv
```

scan処理の要件。

1. t_scan_runに実行開始レコードを作成する
2. configのroots配下を再帰的に探索する
3. 対象拡張子のみ処理する
4. 除外ディレクトリ、除外ファイルをスキップする
5. ファイルパスを正規化する
6. normalized_pathからSHA-256でpath_hashを作る
7. ファイルサイズ、更新日時を取得する
8. 既存レコードがあり、サイズと更新日時が同じ場合は本文抽出をスキップする
9. 新規または更新の場合は本文抽出する
10. 本文をチャンク化する
11. 各チャンクにembeddingを付与する
12. t_file、t_file_chunkをupsertする
13. last_seen_scan_run_idを更新する
14. スキャン対象root配下で今回見つからなかった既存activeファイルはstatus='deleted'にする
15. エラーはt_scan_errorに記録し、スキャン全体は可能な限り継続する
16. 最後にt_scan_runのstatus、件数、finished_atを更新する

# 8. ファイル抽出仕様

app/services/extractor.pyを実装する。

拡張子ごとに抽出する。

* .txt, .md, .csv, .log

  * UTF-8、CP932、Shift-JISを順に試す
* .docx

  * python-docxで段落と表の文字列を抽出
* .xlsx, .xlsm

  * openpyxlでシート名、セル値を抽出
  * 1シートごとにsource_type='sheet'のチャンクにできるよう、シート名を保持
* .pptx

  * python-pptxでスライド内テキストを抽出
* .pdf

  * pypdfでページごとにテキスト抽出
  * ページ番号を保持

.xlsは初期実装では必須対応しない。
対象外または抽出失敗の場合はt_scan_errorに記録する。

抽出結果は以下のような内部構造にする。

```python
@dataclass
class ExtractedSection:
    source_type: str
    text: str
    sheet_name: str | None = None
    page_no: int | None = None
    slide_no: int | None = None
    heading: str | None = None
```

# 9. チャンク分割

app/services/chunker.pyを実装する。

要件。

* 基本チャンクサイズは設定値chunk_size
* overlapは設定値chunk_overlap
* Excelはシート単位を優先する
* PDFはページ単位を優先する
* PPTはスライド単位を優先する
* 長すぎるsectionはさらに文字数で分割する
* 空白だけのチャンクは登録しない
* content_hashをSHA-256で作成する
* token_countは厳密でなくてよい。初期実装では文字数 / 2 程度の概算でよい

# 10. メタデータ推定

app/services/metadata.pyを実装する。

ファイルパス、ファイル名、フォルダ名、本文プレビューから以下を推定する。

* system_name
* project_name
* document_type
* year_label
* version_label
* folder_keywords
* path_keywords
* is_archive
* archive_reason
* latest_group_key
* search_text
* content_preview

仕様。

## document_type

configのmetadata.document_type_keywordsを使って推定する。
ファイル名、パス、本文プレビューの順に重みを高く見る。

## is_archive

パスまたはファイル名に以下が含まれる場合はarchive扱い。

* old
* backup
* bk
* 退避
* 廃止
* 削除
* 旧
* コピー
* 修正前

ただし、単語境界の扱いには注意する。
大文字小文字は無視する。

## latest_group_key

同じ資料の版違いをまとめるキー。
初期実装では以下の正規化で作成する。

* 拡張子を除外
* 日付文字列を除外

  * 20240501
  * 2024-05-01
  * 2024_05_01
* version表記を除外

  * v1
  * v1.0
  * ver1
  * rev2
* 「最新版」「最新」「確定」「正式」「コピー」「修正前」などのノイズ語を除外
* 空白、記号、全角半角の揺れをある程度正規化
* parent_pathの主要部分と正規化ファイル名を連結して作成する

## is_latest_candidate

同じlatest_group_key内で以下を総合して判定する。

* last_modified_atが新しいほど高い
* ファイル名に「最新版」「最新」「確定」「正式」が含まれると加点
* is_archive=trueなら大きく減点
* parent_pathにold、backup、退避、廃止が含まれると大きく減点

スキャン後、同じlatest_group_keyの中で最もスコアが高い1件をis_latest_candidate=trueにする。

# 11. embedding設計

app/services/embedder.pyを実装する。

以下のインターフェースを作成する。

```python
class EmbeddingProvider(Protocol):
    def embed(self, text: str) -> list[float]:
        ...
```

実装。

1. HashEmbeddingProvider

   * 開発・テスト用
   * 外部通信しない
   * textから安定した疑似ベクトルを作る
   * 次元数は1536
   * 意味検索品質はないためREADMEに明記する

2. OpenAICompatibleEmbeddingProvider

   * 環境変数で明示的に有効化された場合のみ使う
   * EMBEDDING_API_BASE
   * EMBEDDING_API_KEY
   * EMBEDDING_MODEL
   * タイムアウトとリトライを実装する
   * APIキーや本文をログ出力しない

# 13. 検索処理

app/services/search_service.pyを実装する。

検索は以下の流れ。

1. クエリ解析
2. メタデータフィルタ作成
3. キーワード検索
4. ベクトル検索
5. 検索結果の統合
6. ACLフィルタ
7. 再ランキング
8. ファイル単位に集約
9. match_reason生成
10. t_search_log登録

## 13.1 クエリ解析

以下を抽出する。

* 文書種別

  * 画面設計書
  * 基本設計書
  * 詳細設計書
  * IF設計書
  * 問い合わせ資料
  * 障害対応資料
  * 議事録
* 年度

  * 2024年度
  * 2025年
* 日付

  * 20240501
  * 2024/05/01
  * 2024-05-01
* 画面ID、機能ID、帳票IDらしい文字列

  * A001
  * USR010
  * BAT001
  * IF001
* エラーコードらしい文字列
* 「最新版」「最新」「現行」が含まれるか

クエリ解析は初期実装ではルールベースでよい。

## 13.2 キーワード検索

対象。

* t_file.file_name
* t_file.file_path
* t_file.search_text
* t_file.folder_keywords
* t_file.path_keywords
* t_file_chunk.content_text

実装方針。

* まずILIKEで確実に動く検索を実装する
* pg_trgmインデックスが使えるようにする
* PGroongaが導入されている場合はPGroonga用検索に切り替え可能にする
* SQLインジェクション対策として必ずバインドパラメータを使う

## 13.3 ベクトル検索

* queryをEmbeddingProviderでembedding化
* t_file_chunk.embeddingに対してcosine distanceで検索
* status='active'のファイルのみ対象
* include_archive=falseの場合はis_archive=falseのみ対象
* top_kより多めに取得する

  * 例: top_k * 5
* embeddingがNULLのチャンクは除外

filtersに指定された以下で絞り込む。

* system_name
* document_type

* updated_from
* updated_to
* include_archive
* latest_only

## 13.5 ACLフィルタ

ACL_MODEを実装する。

* off

  * ACLを無視する
* permissive

  * t_file_aclにレコードがないファイルは閲覧可能扱い
  * ACLがある場合はuser_idまたはgroup_idsに一致するcan_read=trueが必要
* strict

  * user_idまたはgroup_idsに一致するcan_read=trueが必須

初期値はpermissive。

# 14. 再ランキング

app/services/ranking.pyを実装する。

検索結果の最終順位は、以下の要素で決める。

スコアは0.0から1.0に正規化して返す。

加点要素。

* ファイル名にクエリ重要語が完全一致
* ファイル名に画面ID、機能ID、障害IDが一致
* パスにシステム名、年度、保守、障害、設計などが一致
* document_typeが一致
* system_nameが一致
* チャンク本文が一致
* ベクトル類似度が高い
* is_latest_candidate=true
* 更新日時が新しい

減点要素。

* is_archive=true
* パスにold、backup、退避、廃止、削除が含まれる
* ファイル名にコピー、修正前、旧が含まれる
* queryが最新版系なのにis_latest_candidate=false

重みはconfigから変更可能にする。

match_reasonを必ず生成する。
match_reasonは、なぜ候補になったかをユーザーに説明できる短い日本語配列にする。

例。

```json
[
  "ファイル名に 'A001' が一致",
  "文書種別が '画面設計書' と推定されました",
  "フォルダに '顧客管理システム' が含まれます",
  "old/backupフォルダではありません",
  "同一資料グループ内の最新版候補です"
]
```

# 15. 重要な制約

絶対に守ること。

1. 検索APIはDBに存在するファイル名とファイルパスだけを返す
2. 存在しないファイルパスを生成しない
3. 抽出本文やAPIキーをログに出さない
4. 読み取り失敗したファイルでスキャン全体を止めない
5. 削除済みファイルは通常検索結果に出さない
6. include_archive=falseの場合、archive扱いのファイルは出さない
7. Dify連携処理は今回実装しない
8. 不明な要件があっても実装を止めず、合理的な仮定をREADMEに明記する
